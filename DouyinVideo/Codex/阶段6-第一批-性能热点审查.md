# 阶段 6 第一批：性能热点审查

日期：2026-06-16  
目标：在不修改游戏运行代码的前提下，审查当前项目中影响长时间录制流畅度的代码热点，并给后续安全优化分批定边界。

## 本批范围

本批只做审查和文档整理。

没有改动：

1. 游戏代码。
2. Prefab、Scene、Inspector 绑定。
3. 玩法数值。
4. 协程时序。
5. 物理查询逻辑。
6. UI、战报、音效表现。

## 审查方法

本批重点搜索并阅读以下类型代码：

| 类型 | 搜索重点 |
|---|---|
| 每帧逻辑 | `Update`、`FixedUpdate`、`while(true)`、`yield return null` |
| 对象分配 | `Instantiate`、`Destroy`、`new WaitForSeconds`、数组查询 |
| 查找和组件获取 | `GetComponent`、`transform.Find`、`Camera.main` |
| 物理查询 | `Raycast`、`RaycastAll`、`OverlapCircleAll` |
| UI 压力 | `Broadcast`、`Canvas.ForceUpdateCanvases`、`LineRenderer`、DOTween |
| 音频压力 | `AudioManager.PlaySFX`、`PlayOneShot` |
| 日志压力 | `Debug.Log`、`Debug.LogWarning` |

## 总体结论

当前最值得关注的性能热点不是单一脚本，而是几类重复模式：

| 优先级 | 热点 | 说明 |
|---|---|---|
| 高 | 战报 UI 频繁实例化和强制刷新 | `Broadcast.BroadCastNews` 每次实例化文本并 `Canvas.ForceUpdateCanvases()` |
| 高 | 音效对象频繁实例化和销毁 | `AudioManager.PlaySFX` 每次创建 `AudioSource`，角色碰撞会频繁触发 |
| 中高 | 飞光 UI 和能量球 Instantiate/Destroy | 大招点飞光和能量球会持续创建销毁对象 |
| 中高 | 激光/范围技能的物理查询分配 | `RaycastAll`、`OverlapCircleAll` 会分配数组，但改法有命中顺序风险 |
| 中 | 多个调试 `Update` | 轮询按键本身不重，但数量多，后续可统一标注或条件编译 |
| 中 | `Debug.Log` 高频输出 | 伤害、射线、范围检测等日志可能拖慢 Editor 录制 |
| 高风险暂不动 | `BaseRole.FixedUpdate` | 直接决定小球自动运动，是核心玩法手感 |

## 对象创建与销毁热点

### 战报 UI

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `Assets/Scripts/Broadcast.cs` | `Instantiate(broadText, textParent)` | 每条战报创建一个 Text |
| `Assets/Scripts/Broadcast.cs` | `Canvas.ForceUpdateCanvases()` | 每条战报强制刷新 UI 布局 |

影响：

1. 火墙、烟男、武器命中、淘汰等都会频繁播报。
2. 战报越多，ScrollRect 内容越重。
3. `Canvas.ForceUpdateCanvases()` 会强制 UI 立即刷新，录制时容易产生卡顿尖峰。

建议：

| 批次 | 建议 |
|---|---|
| 阶段 6 第二批 | 先不改战报池，记录战报条数和调用频率 |
| 阶段 6 第三批 | 设计 `Broadcast` 文本对象池，并确认 ScrollRect 滚动行为不变 |

### 音效

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `Assets/Scripts/Audio/AudioManager.cs` | `Instantiate(sfxSourcePrefab, transform)` | 每个音效创建 AudioSource |
| `Assets/Scripts/Audio/AudioManager.cs` | `Destroy(sfx.gameObject, clip.length / pitch)` | 音效播完销毁 |
| `Assets/Scripts/BaseRole.cs` | `OnCollisionEnter2D` 调用 `AudioManager.Instance.PlaySFX("撞击")` | 小球频繁碰撞时触发很多音效对象 |

影响：

1. 自动乱斗中角色和墙体/角色碰撞频繁。
2. 每次碰撞都创建和销毁音效对象，容易造成 GC 和对象生命周期压力。

建议：

| 批次 | 建议 |
|---|---|
| 阶段 6 第三批 | 优先把 SFX 做对象池试点 |
| 注意 | 必须保持多音效可重叠播放，不能改成单 AudioSource 覆盖播放 |

### 大招球和飞光

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `Assets/Scripts/VideoGameManager.cs` | `Instantiate(bigBallPrefab, randomPos, Quaternion.identity)` | 每 4 秒生成大招球 |
| `Assets/Scripts/BaseRole.cs` | `Destroy(collision.gameObject)` | 大招球拾取后销毁 |
| `Assets/Scripts/VideoGameManager.cs` | `Instantiate(flyLightPrefab, canvasTransform)` | 每次获得大招点创建飞光 |
| `Assets/Scripts/VideoGameManager.cs` | `Destroy(flyCoin)` | DOTween 结束后销毁飞光 |
| `Assets/Scripts/RoleUI.cs` | `AttackOther` 调用 `PlayFlyEffect` | 每次加大招点触发默认 3 个飞光 |

影响：

1. 大招球是持续生成对象，适合对象池。
2. 飞光是 UI 动画对象，可能短时间产生多个。
3. 飞光使用 DOTween，回收前必须处理 Tween 生命周期。

建议：

| 批次 | 建议 |
|---|---|
| 阶段 6 第三批 | 飞光对象池可作为 UI 对象池试点 |
| 阶段 6 第四批 | 大招球对象池需要确认 `OnBallGenerate` 和拾取销毁逻辑不变后再做 |

### 状态图标

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `Assets/Scripts/BaseRole.cs` | `Instantiate(CantGetWeaponPrefab, effectParent)` | 每次禁用拾取创建图标 |
| `Assets/Scripts/BaseRole.cs` | `Instantiate(CantUseBigPrefab, effectParent)` | 每次禁用大招创建图标 |
| `Assets/Scripts/BaseRole.cs` | `Destroy(icon.gameObject)` | 状态结束时销毁图标 |

影响：

状态图标频率比碰撞音效和战报低，优先级较低。

建议：

先不作为阶段 6 第二批重点，等对象池方案稳定后再考虑。

### 核心移动

证据：

| 文件 | 代码点 | 风险 |

## 物理查询与分配

### RaycastAll

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `FireWallFireManRole.cs` | 火墙持续 5 秒，每帧 `Physics2D.RaycastAll` | 数组分配，命中顺序敏感 |
| `BanXianBaoAnRole.cs` | 绊线激光激活后 `while(true)` 中 `Physics2D.RaycastAll` | 数组分配，命中顺序敏感 |

结论：

`RaycastAll` 可优化为 `RaycastNonAlloc`，但风险偏高：

1. 需要固定缓冲区大小。
2. 命中顺序必须确认不变。
3. 如果缓冲区过小，可能漏判。
4. 火墙和绊线的命中逻辑都依赖第一个合适目标。

建议：

阶段 6 第二批不动。后续若做，必须单英雄试点。

### OverlapCircleAll

证据：

| 文件 | 代码点 | 风险 |
|---|---|---|
| `WeiSiRole.cs` | `Physics2D.OverlapCircleAll(center, radius)` | 一次性数组分配 |

结论：

维斯的大招只在 3 秒等待后检测一次，性能风险不高。可以作为后期低风险优化候选，但不急。

### 普通 Raycast

证据：

| 文件 | 代码点 |
|---|---|
| `NiHongRole.cs` | 激光持续期间每帧 `Physics2D.Raycast` |
| `DiJiaRole.cs` | 激光持续期间每帧 `Physics2D.Raycast` |
| `LieXiaoRole.cs` | 激光延伸期间每帧 `Physics2D.Raycast` |

结论：

普通 `Raycast` 返回结构体，不像 `RaycastAll` 那样直接数组分配。当前优先级低于 `RaycastAll`。

## Debug.Log 热点

证据：

| 文件 | 说明 |
|---|---|
| `BaseRole.cs` | 受伤、死亡、使用大招会输出日志 |
| `NiHongRole.cs` | 激光循环中输出命中对象 |
| `WeiSiRole.cs` | 范围内每个物体输出日志 |
| `JieFengRole.cs` | 发射飞镖时输出目标 |
| `QianBaoRole.cs` | 命中角色/墙体时输出弹道信息 |
| `FireWallFireManRole.cs` | 锁定目标、火墙结束、回血输出日志 |

影响：

Unity Editor 打开 Console 时，高频日志会明显影响录制流畅度。尤其是激光持续期间每帧或高频输出的日志。

建议：

阶段 6 第二批可以优先处理高频 Debug 日志，但要确认你是否依赖这些日志调试。保守做法是先只清理明显高频日志，不动错误和关键状态日志。

## 风险分层

### 低风险，可优先进入阶段 6 第二批

| 项 | 理由 |
|---|---|
| 清理空 `LaserShooter.Update` | 空方法，不影响玩法 |
| 清理或注释高频 `Debug.Log` | 不影响 gameplay，但会影响调试可见性 |
| 局部缓存低频但重复的组件引用 | 如烟男、钢索的局部变量缓存，需逐文件确认 |
| 给性能热点补中文注释 | 不影响运行 |

### 中风险，适合阶段 6 第三批对象池试点

| 项 | 理由 |
|---|---|
| SFX AudioSource 对象池 | 需要保证多音效重叠、pitch、销毁时间表现不变 |
| 战报 Text 对象池 | 需要保证 ScrollRect 和布局刷新表现不变 |
| 飞光 UI 对象池 | 需要正确 Kill/重置 DOTween |
| 大招球对象池 | 需要替换销毁路径，影响 `OnBallGenerate` 和拾取逻辑 |

### 高风险，暂不建议动

| 项 | 原因 |
|---|---|
| 改 `BaseRole.FixedUpdate` | 直接改变小球运动轨迹和录制节奏 |
| 全局替换 `RaycastAll` 为 `RaycastNonAlloc` | 可能改变命中顺序或漏判 |
| 全局停止胜利后的所有协程 | 可能改变胜利画面和收尾效果 |
| 一次性引入全局对象池框架 | 生命周期复杂，容易影响现有表现 |
| 缓存 `VideoGameBulletBase` 的 Rigidbody2D | 捷风运行时组件变化会受影响 |

## 后续分批建议

| 批次 | 内容 | 是否改代码 | 说明 |
|---|---|---|---|
| 阶段 6 第二批 | 低风险日志、空 Update、局部缓存整理 | 是 | 不改玩法、不改对象生命周期 |
| 阶段 6 第三批 | 音效对象池试点 | 是 | 优先 SFX，收益明显，范围可控 |
| 阶段 6 第四批 | 战报/飞光 UI 对象池设计和试点 | 是 | 需要处理 DOTween 和布局刷新 |
| 阶段 6 第五批 | 物理查询 NonAlloc 单英雄试点 | 是 | 只选一个英雄验证，不全局替换 |
| 阶段 6 第六批 | 胜利后收尾稳定性审查 | 文档优先 | 明确哪些循环可停、哪些不能停 |

## 本批结论

1. 当前最优先的性能收益点是音效、战报、飞光这类对象生命周期。
2. `BaseRole.FixedUpdate` 和 `RaycastAll` 不是不能优化，而是不能先动。
3. 阶段 6 第二批应选择非常低风险的小清理，为后续对象池试点铺路。
4. 所有性能优化都必须保持录制画面节奏，不以“更合理”为理由改变玩法表现。
