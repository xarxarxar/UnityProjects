# 新增玩法机制指南

本指南用于未来添加观众爱看的玩法机制，例如上厕所机制、随机事件、场地机关、Buff/Debuff 等。

## 机制定位

当前项目只有正常模式。  
未来可以增加娱乐模式，在正常模式的基础上附加奇怪机制。

现阶段不需要提前实现复杂模式系统，但新增机制时应避免污染正常模式核心代码。

模式边界设计见：`Codex/阶段3-模式边界设计.md`。
机制配置和 Inspector 规范见：`Codex/阶段3-机制配置与Inspector规范.md`。
娱乐机制最小入口设计见：`Codex/阶段3-娱乐机制最小入口设计.md`。
上厕所机制最小试点见：`Codex/阶段3-第四批-上厕所机制最小试点.md`。

## 基本原则

1. 新机制优先独立成组件或 Manager。
2. 不直接塞进 `BaseRole`，除非它是所有英雄永远都需要的基础能力。
3. Inspector 只暴露少量关键配置。
4. 机制是否启用应清晰可控。
5. 机制引发的扣血、停速、恢复等效果，优先调用 `BaseRole` 已有接口。

## 推荐结构

以“上厕所机制”为例，推荐拆成：

| 脚本 | 职责 |
|---|---|
| `ToiletMechanismManager` | 机制总控，负责启用、计时、广播、规则协调 |
| `RoleToiletState` | 挂在角色上，记录便意值、是否正在上厕所 |
| `ToiletArea` | 厕所区域，检测角色进入 |
| `ToiletSpawner` | 随机生成厕所位置 |
| `ToiletConfig` | 可选配置数据，控制阈值、扣血、持续时间等 |

## 正常模式与娱乐模式

短期建议：
- 正常模式不启用娱乐机制。
- 娱乐机制是否启用通过一个总控开关决定。
- 当前上厕所机制已有最小试点脚本，但默认关闭且未绑定场景。
- 不为了单个试点新增空的 `GameModeManager`。

未来可能结构：

```csharp
public enum GameMode
{
    Normal,
    Fun
}
```

注意：现在不一定要实现这个枚举。只有当第一个娱乐机制真正加入时，再决定是否落代码。

## 机制边界提醒

| 规则 | 说明 |
|---|---|
| 不塞进 `BaseRole` | 机制状态优先独立成组件，例如 `RoleToiletState` |
| 不污染正常模式 | 未启用娱乐机制时，当前自动乱斗表现应保持一致 |
| 不重写核心系统 | 娱乐机制通过公开接口调用伤害、速度、播报 |
| 不过度 Inspector 化 | 只暴露关键开关和少量参数 |

## Inspector 配置建议

适合放 Inspector：
- 是否启用机制。
- 机制相关 Prefab。
- 基础数值，如间隔、阈值、伤害、持续时间。
- 生成区域或父节点引用。
- 调试开关，例如是否打印日志。

不适合全部放 Inspector：
- 复杂规则组合。
- 每个英雄的细碎开关。
- 大量重复配置。
- 正常模式核心规则。

默认值建议：
- 娱乐机制默认关闭。
- 调试日志默认关闭。
- 机制数值默认保守。
- 如果要让某个娱乐机制默认启用，必须先更新机制文档和 `Codex/修改记录.md`。

## 机制开发流程

1. 先写机制设计说明，放入 `Codex/`。
2. 明确机制是否默认启用。
3. 明确是否影响正常模式。
4. 明确机制需要访问哪些系统。
5. 按 `Codex/阶段3-娱乐机制最小入口设计.md` 确认最小入口。
6. 先实现最小可运行版本。
7. 记录到 `Codex/修改记录.md`。
8. 手动验证完整局表现。

## 上厕所机制示例草案

机制名称：上厕所机制  
机制类型：娱乐机制  
默认是否启用：否  

规则草案：
1. 场景中随机出现卫生间。
2. 英雄拥有便意值。
3. 便意值随时间增长。
4. 便意值达到最大且未进入厕所时，持续扣血。
5. 英雄进入厕所区域后强制停留 5 秒。
6. 停留结束后便意清零。

实现注意：
- 便意状态不直接写入 `BaseRole`。
- 扣血调用 `BaseRole.TakeDamage`。
- 停止移动调用现有速度控制接口。
- 播报使用统一播报入口。
