# 阶段 3 第三批：娱乐机制最小入口设计

日期：2026-06-16  
目标：在不修改游戏代码的前提下，明确未来第一个娱乐机制真正落地时，最小需要哪些入口、脚本和验证点。

## 当前结论

本批不新增运行时代码。  
本批只设计“第一个娱乐机制”的最小入口方案。

更新：阶段 3 第四批已按本文档落地“上厕所机制”最小试点脚本，见 `Codex/阶段3-第四批-上厕所机制最小试点.md`。该试点默认关闭，且未绑定到场景。

原因：

1. 当前尚未确定第一个真正要实现的娱乐机制。
2. 没有具体机制时新增 `GameModeManager` 或总控代码，无法验证是否合适。
3. 当前正常模式仍需优先保护。
4. 最小入口设计可以先指导未来实现，避免到时候乱接进 `BaseRole` 或 `VideoGameManager`。

## 什么时候才落代码

满足以下条件后，才开始新增娱乐机制运行时代码：

| 条件 | 是否必须 |
|---|---|
| 已确定机制名称和规则 | 必须 |
| 已写机制设计文档 | 必须 |
| 已确认默认是否启用 | 必须 |
| 已确认是否影响正常模式 | 必须 |
| 已列出 Inspector 配置 | 必须 |
| 已列出人工验证点 | 必须 |
| 已确认需要哪些 Prefab 或场景对象 | 视机制需要 |

如果以上信息不完整，只写文档，不写代码。

## 最小入口包

第一个娱乐机制落地时，建议只新增它自己需要的入口，不先做完整模式系统。

推荐最小包：

| 文件/对象 | 是否建议 | 作用 |
|---|---|---|
| `具体机制Manager` | 必须 | 机制总控，负责启用开关、计时、生成、规则协调 |
| `角色机制状态组件` | 视机制需要 | 存放单个角色在该机制下的状态 |
| `机制区域/道具组件` | 视机制需要 | 处理场景触发区域、道具、机关 |
| `机制配置字段` | 必须 | 少量 Inspector 字段或小型 Config |
| `机制文档` | 必须 | 记录规则、默认值、风险、验证点 |
| `EntertainmentMechanismManager` | 暂不建议 | 等至少两个娱乐机制都需要统一调度时再加 |
| `GameModeManager` | 暂不建议 | 等确实需要 Normal/Fun 模式切换时再加 |
| `GameMode enum` | 暂不建议 | 等模式切换真实出现时再加 |

## 推荐接入点

| 需求 | 推荐接入点 | 不推荐 |
|---|---|---|
| 启用/关闭机制 | 机制 Manager Inspector 开关 | 改 `VideoGameManager` 主流程 |
| 访问全部角色 | `VideoGameManager.instance.circleRoles` 只读遍历 | 修改角色列表含义 |
| 给角色加机制状态 | 机制 Manager 运行时查找或添加组件 | 把字段加进 `BaseRole` |
| 对角色扣血 | `BaseRole.TakeDamage` 或 `VideoGameCombatUtility` | 自己复制死亡判断 |
| 控制角色速度 | `BaseRole.SetSpeed` | 直接改 Rigidbody 速度规则 |
| 播报 | `Broadcast.instance` 或 `VideoGameCombatUtility` | 新建一套播报系统 |
| 音效 | `AudioManager` 或角色现有 `PlayAudio` | 新建重复音频入口 |

## 不允许的最小入口

第一个娱乐机制不应该做这些事：

1. 不修改胜负条件。
2. 不修改武器刷新规则。
3. 不修改能量球生成规则。
4. 不修改 `BaseRole.FixedUpdate` 移动驱动。
5. 不把机制状态字段塞进 `BaseRole`。
6. 不在每个英雄脚本里写机制判断。
7. 不为了一个机制新增完整模式框架。

## 上厕所机制最小入口示例

如果第一个机制选择“上厕所机制”，建议最小入口如下：

| 脚本 | 是否需要 | 职责 |
|---|---|---|
| `ToiletMechanismManager` | 必须 | 总控开关、便意增长、扣血调度；厕所生成后续按需加入 |
| `RoleToiletState` | 必须 | 记录便意值、是否在厕所、是否正在强制停留 |
| `ToiletArea` | 必须 | 检测角色进入厕所范围 |
| `ToiletConfig` | 可选 | 当配置字段较多时再拆 |

推荐数据流：

```text
ToiletMechanismManager.enableToiletMechanism
→ 遍历 VideoGameManager.instance.circleRoles
→ 给角色查找或添加 RoleToiletState
→ RoleToiletState 记录便意
→ ToiletArea 通知角色进入厕所
→ BaseRole.SetSpeed / BaseRole.TakeDamage
→ Broadcast / Audio 表现
```

默认值建议：

| 配置 | 默认值 |
|---|---|
| `enableToiletMechanism` | `false` |
| `urgeIncreaseInterval` | `2f` |
| `maxUrge` | `100` |
| `damagePerTick` | `5` |
| `damageInterval` | `1f` |
| `stayDuration` | `5f` |
| `showDebugLog` | `false` |

## 机制 Manager 推荐职责

机制 Manager 应该负责：

1. 保存启用开关。
2. 保存少量 Inspector 配置。
3. 初始化机制需要的运行时对象。
4. 遍历当前角色并挂接状态组件。
5. 驱动机制全局计时或生成。
6. 调用已有公开接口产生效果。
7. 在 `gameEnd` 后停止或忽略无意义逻辑。

机制 Manager 不应该负责：

1. 管理全部游戏流程。
2. 判断最终胜者。
3. 替代 `VideoGameManager`。
4. 直接改角色移动底层。
5. 直接改武器和能量球刷新规则。

## 角色机制状态组件推荐职责

角色机制状态组件应该负责：

1. 保存某个角色在该机制中的状态。
2. 提供清晰方法给 Manager 调用。
3. 只依赖 `BaseRole` 的公开接口。
4. 在角色死亡或游戏结束时停止自身机制效果。

角色机制状态组件不应该负责：

1. 自己查找所有角色。
2. 自己生成全局场景对象。
3. 自己决定胜负。
4. 保存多个机制的混合状态。

## 代码落地顺序

当真的开始实现第一个机制时，建议按这个顺序：

1. 在 `Codex/` 新增机制设计文档。
2. 新增机制 Manager，默认关闭。
3. 新增角色状态组件。
4. 新增区域或道具组件。
5. 只接入一个最小效果。
6. 记录到 `Codex/修改记录.md`。
7. 人工验证正常模式未受影响。
8. 再逐步补充表现和数值。

| 验证项 | 说明 |
|---|---|
| 机制关闭时 | 当前正常模式表现完全一致 |
