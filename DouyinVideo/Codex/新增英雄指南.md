# 新增英雄指南

本指南用于后续新增英雄时保持脚本结构清晰、行为可追踪、方便录制调试。

## 基本原则

1. 新英雄继续继承 `BaseRole`。
2. 英雄大招可以单独写，不强行套统一模板。
3. 基础能力尽量复用已有接口或工具类。
4. 不把娱乐机制直接写进英雄大招，除非这个机制就是该英雄的特色。
5. 调试按键必须放在清晰的开发调试区域。

| 需求 | 推荐工具 |
|---|---|
| 随机选择其他角色 | `VideoGameTargetUtility.GetRandomOther` 或 `otherBaseRole` |
| 计算朝目标方向 | `VideoGameAimUtility.GetDirection` |
| 让表现物朝向目标 | `VideoGameAimUtility.AimZAxisAtTarget` |
| 先播报再伤害 | `VideoGameCombatUtility.BroadcastThenDamage` |
| 先伤害再播报 | `VideoGameCombatUtility.DamageThenBroadcast` |

| 禁用大招或禁拾武器并播报 | `VideoGameCombatUtility.SetCanUseBigThenBroadcast`、`VideoGameCombatUtility.SetCanGetWeaponThenBroadcast` |

## 推荐脚本结构

```csharp
public class XxxRole : BaseRole
{
    #region 字段配置
    #endregion

    #region 协程引用
    #endregion

    #region Unity生命周期
    #endregion

    #region 大招逻辑
    #endregion

    #region 开发调试入口
    #endregion

    #region 工具方法
    #endregion
}
```

不是每个区域都必须存在。小脚本不要为了分区而分区。

旧英雄整理时，不要为了套模板改变原有执行顺序。尤其不要同时修改协程顺序、数值、Layer、Collider、父子关系和命中回调。

## 大招推荐结构

```csharp
/// <summary>
/// 释放英雄大招。
/// </summary>
public override void Big()
{
    // 停止旧协程
    // 启动新协程
}

/// <summary>
/// 执行大招流程。
/// </summary>
/// <returns>Unity 协程迭代器。</returns>
private IEnumerator BigCoro()
{
    // 前摇
    // 播报
    // 表现
    // 命中判定
    // 结算
    // 收尾
}
```

## 字段建议

Inspector 需要配置的字段使用 `public` 或 `[SerializeField] private`，并添加 `[Tooltip("说明")]`。

示例：

```csharp
[Tooltip("大招前摇时间")]
[SerializeField] private float bigDelay = 1.5f;
```

如果字段会被其他脚本直接访问，保留 `public`。  
如果只在本脚本内部使用，优先 `[SerializeField] private`。

## 调试入口规范

开发调试入口可以保留，但必须标注。

```csharp
#region 开发调试入口

private void Update()
{
    if (Input.GetKeyDown(KeyCode.M))
    {
        UseBig();
    }
}

#endregion
```

后续如果调试入口变多，可以统一迁移到调试工具类。

## 新增英雄后验证

| 验证项 | 说明 |
|---|---|
| 自动移动 | 英雄能正常弹动 |
| 吃能量球 | 能获得大招点 |
| 大招释放 | 大招点满后能自动释放 |
| 受伤 | 能正确扣血 |
| 死亡 | HP 归零后能淘汰 |
| 胜利 | 最后一人时胜利表现正常 |
| 多次释放 | 大招重复释放不残留异常状态 |
| 被其他技能影响 | 减速、禁用大招、禁拾武器等状态正常 |

## 不建议现在做

| 不建议项 | 原因 |
|---|---|
| 新建另一套角色父类 | 当前所有英雄仍依赖 `BaseRole` |
| 把多个英雄大招强行合并成一个模板 | 大招差异很大，合并容易损坏特色表现 |
| 把娱乐机制写进每个英雄脚本 | 后续会导致脚本膨胀和维护困难 |
| 未记录就复制旧英雄脚本改名 | 出问题后难以追踪来源 |
