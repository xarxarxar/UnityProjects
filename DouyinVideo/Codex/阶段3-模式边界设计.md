# 阶段 3 第一批：模式边界设计

日期：2026-06-16  
目标：在不修改游戏代码的前提下，明确正常模式和娱乐模式的边界，为未来新增奇怪机制预留结构方向。

## 当前结论

当前项目只有正常模式。  
本批不新增 `GameModeManager`，不新增模式枚举，不新增机制开关代码。

原因：

1. 现在还没有真正落地的娱乐机制。
2. 过早写模式系统容易变成空架子。
3. 当前最重要的是保护已有自动乱斗表现不被未来机制污染。
4. 等第一个娱乐机制真正要实现时，再按本文件落最小代码结构。

## 模式定义

| 模式 | 定义 | 当前状态 |
|---|---|---|
| 正常模式 | 当前已有自动乱斗玩法：角色自动弹动、拾取武器、吃能量球、释放大招，直到出现胜者 | 已存在，必须优先保护 |
| 娱乐模式 | 在正常模式基础上附加观众爱看的奇怪机制，例如上厕所、随机场地事件、临时 Buff/Debuff | 仅文档预留，暂不实现 |

## 正常模式保护原则

1. 正常模式必须是当前默认行为。
2. 没有明确启用娱乐机制时，游戏表现应与当前一致。
3. 娱乐机制不能改变正常模式的基础规则。
4. 娱乐机制不能默认影响武器刷新、能量球生成、胜负判断。
5. 娱乐机制不能散落到每个英雄脚本中。
6. 娱乐机制不能把 `BaseRole` 变成大杂烩。

## 娱乐机制放置边界

| 内容 | 推荐位置 | 不推荐位置 |
|---|---|---|
| 全局机制调度 | 独立 Manager，例如 `ToiletMechanismManager` | `VideoGameManager` 主流程里硬塞大量机制逻辑 |
| 单个角色的机制状态 | 独立组件，例如 `RoleToiletState` | `BaseRole` 字段持续膨胀 |
| 机制区域检测 | 独立区域组件，例如 `ToiletArea` | 写进角色碰撞逻辑 |
| 机制生成逻辑 | 独立 Spawner 或 Manager | 武器刷新函数里混入娱乐机制 |
| 机制配置 | 小型 Config 或 Manager Inspector 字段 | 每个英雄 Prefab 上大量重复配置 |
| 机制表现播报 | 调用现有 `Broadcast` 或 `VideoGameCombatUtility` | 复制多套播报入口 |

## 未来最小落地结构

当第一个娱乐机制真正开始实现时，建议按以下最小结构落地：

| 脚本 | 是否必须 | 职责 |
|---|---|---|
| `VideoGameModeSettings` | 可选 | 存放当前是否启用娱乐机制、启用哪些机制 |
| `EntertainmentMechanismManager` | 可选 | 统一管理娱乐机制启停 |
| `具体机制Manager` | 必须 | 管理某个具体机制的规则、计时、生成、播报 |
| `角色机制状态组件` | 视机制需要 | 挂在角色上，保存该机制对单个角色的状态 |
| `机制区域/道具组件` | 视机制需要 | 处理触发区域、临时道具、场景对象 |

注意：  
如果未来只有一个娱乐机制，可以先不做 `EntertainmentMechanismManager`，只做一个具体机制 Manager。  
不要为了“架构完整”提前增加多层抽象。

## 推荐数据流

娱乐机制建议遵循以下方向：

```text
机制开关/配置
→ 机制 Manager
→ 角色机制状态组件 / 场景机制对象
→ BaseRole 现有公开接口
→ UI / Broadcast / Audio
```

示例：

```text
上厕所机制启用
→ ToiletMechanismManager 计时和机制调度，厕所生成后续按需加入
→ RoleToiletState 记录便意
→ BaseRole.SetSpeed / BaseRole.TakeDamage
→ Broadcast 播报表现
```

## Inspector 配置边界

适合放 Inspector：

| 配置 | 示例 |
|---|---|
| 是否启用机制 | `enableToiletMechanism` |
| 关键数值 | 便意增长间隔、扣血值、停留时间 |
| Prefab 引用 | 厕所 Prefab、提示特效 |
| 生成范围引用 | 场地边界、生成点父物体 |
| 调试开关 | 是否显示调试日志 |

不适合放 Inspector：

| 内容 | 原因 |
|---|---|
| 每个英雄一堆单独开关 | 配置量会爆炸 |
| 复杂规则组合 | 难以追踪，建议写在代码和文档里 |
| 正常模式核心规则 | 容易误改录制表现 |
| 大量重复数值 | 后续维护困难 |

## 上厕所机制接入示例

如果未来实现“上厕所机制”，建议结构如下：

| 脚本 | 职责 |
|---|---|
| `ToiletMechanismManager` | 管理机制启用、便意增长、整体规则；厕所生成后续按需加入 |
| `RoleToiletState` | 记录单个角色便意、是否正在厕所中、是否正在扣血 |
| `ToiletArea` | 检测角色进入厕所区域 |
| `ToiletConfig` | 可选，用于记录阈值、扣血、停留时间等 |

推荐流程：

1. 正常模式默认不挂或不启用 `ToiletMechanismManager`。
2. 娱乐模式启用后，Manager 给每个角色添加或查找 `RoleToiletState`。
3. `RoleToiletState` 只记录便意，不继承 `BaseRole`。
4. 扣血调用 `BaseRole.TakeDamage` 或 `VideoGameCombatUtility`。
5. 停止移动调用 `BaseRole.SetSpeed(0, duration)`。
6. 播报调用现有 `Broadcast`。

不建议：

1. 直接把 `lashiValue` 这类机制字段继续塞进 `BaseRole`。
2. 在每个英雄大招里判断便意。
3. 在武器系统里处理厕所机制。
4. 让厕所机制默认影响正常模式。
